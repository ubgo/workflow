# Choose a driver

Which backend runs your workflows: the in-process memory driver, the SQL driver on SQLite, Postgres or MySQL 8, the Redis driver, or the Hatchet engine; and whether to put a wrapper in front of it (hybrid placement, failover, regional routing, a backend cutover) or a shared limit around its steps (pools). Your workflow code is the same on every driver; the choice decides what survives a restart, how many machines can share the work, what you have to operate, and which features are available. The core refuses at `Register`, `Start`, `Enqueue` or `Schedule` what a driver cannot do ([`CheckCaps`](ds:block?id=checkcaps-eg44ezuh) over [`Requires`](ds:block?id=requires-6tcjbcfj), [`RequiresJob`](ds:block?id=requiresjob-mrfs7vqd) and [`RequiresSchedule`](ds:block?id=requiresschedule-wk3hrhfy)), so a wrong choice shows up as an error naming the missing capability, not as silently lost work.

## Memory, SQL, Redis or Hatchet

### What Hatchet refuses

The Hatchet driver declares ([`caps`](ds:block?id=hatchet-caps-d6x9fv8z)) `Durable`, `DelayedStart`, `WaitForEvent`, `WaitOwnRun`, `DurableSleep`, `ConcurrencyKey`, `RateLimit`, `IdempotencyKey`, `Cron`, `Cancel`, `Queue`, `RunQuery`, `CancelAll`, `RetryRun`, `ScheduleList`, `Drain`, `DrainReport`, `ScheduleTrigger`, `ScheduleHistory`, `EnqueueOnly`, `Tenant`, `TickTime`, `DueQuery`, `Result`, `CronSeconds` and `KeyFIFO`, plus `PauseWorkflow` and `SchedulePause` when `Config.API` is set ([`capabilities`](ds:block?id=hatchet-client-capabilities-3ms5edtr)). Grouped by what you would notice (every refusal and difference, with the engine fact behind it, is in [Hatchet › Limitations](../drivers/hatchet.md#limitations)):

| Area | Missing on Hatchet | What to do instead |
|---|---|---|
| Run ends | `CapRunFinished`: `OnRunFinished` is best effort (polled) | Keep a fallback: a TTL for `UniqueUntilFinished`, a poller for batches, the recorder's `Reconciler` |
| Retries | `CapRetryJitter`, `CapRetryDelay` (`DelayFor`, `RetryAfter`), `CapJobRetry`, `CapRetryUntil`, `CapRetryMaxErrors`, `CapDiscard`, `CapDiscardExhausted`, `CapSnooze`, `CapHeartbeat` | Plain `Max` and a `Backoff` whose `Initial` equals `Factor` seconds; a `Snooze` is an ordinary error there and spends an attempt |
| Schedules | the three misfire policies, `CapCronZone` (UTC only; [`checkSupported`](ds:block?id=hatchet-checksupported-733uwgsp)), `CapScheduleWhen`, `CapScheduleWindow`, `CapTickEvents`, `CapOverlapSkip`, `CapScheduleActive`, `CapScheduleKeep` | Crons in UTC; a tick missed while the engine was down is dropped; put schedules that need more on sqlstore or Redis, or use [hybrid placement](#hybrid-failover-regional-cutover-or-pools) |
| Run shape | `CapChain`, `CapWorkflowVersion`, `CapRunTimeout`, `CapSlotCost`, `CapClosure` | Child runs instead of chains ([Hatchet: use child runs](../workflows/chains.md#hatchet-use-child-runs)); a new workflow name instead of a version; `Step.Timeout` per step, which the worker enforces with `ErrStepTimeout` as the other drivers do |
| Idempotency keys | A key holds until the run's first step ends, not until the run ends; a delayed start with a key starts at once on a hidden copy of the workflow whose start gate sleeps until `RunAt` (the key holds until then), refused on a workflow with a `Concurrency` or past `Config.IdempotencyMaxHold`, and cannot be rescheduled ([`errRescheduleGated`](ds:block?id=hatchet-errreschedulegated-9akd6fmr)) | [Unique jobs](../reliability/unique-jobs.md) for a hold until the run ends; `Cancel` and `Enqueue` again to move a keyed delayed start |
| Queues and fairness | `CapQueueOverride`, `CapPauseQueue`, `CapQueueLimitGlobal`, `CapWorkerScale`, `CapRoundRobin`, `CapKeyWeights`; `QueueConfig.Weight` and `Priority` are refused | One Hatchet worker per queue, equal turns between keys |
| Operations and history | `CapDeleteRun`, `CapForceRun`, `CapErrorHistory`, `CapNodeIdentity`, `CapRunStates`, `CapShutdownRequeue`, `CapLabelPrefix`, `CapPayloadSearch`; no `EditRun`, `ResetRun`, `ForkRun` or `SignalWaiting` | The engine's dashboard; `Retry` for a failed run; the [run recorder](../observability/run-recorder.md#per-driver) keeps every attempt's error |
| Per-key state | concurrency keys as Go functions, so [virtual objects](../workflows/objects.md#before-you-start) and [state machines](../workflows/state-machines.md#drivers-and-storage) are refused at `Register` ([`checkSupported`](ds:block?id=hatchet-checksupported-733uwgsp)); no `RunSignalReader`, so `OnSignals` handlers are refused | Run those workflows on another driver |

### If X, then Y

- **If it is a test of your app code**, use [`workflowtest.NewFake(workflowtest.FakeLike(prod))`](ds:block?id=workflowtest-fakelike-my3v73nf), which runs nothing and refuses what production would ([Behave like your production driver](../testing/fake.md#behave-like-your-production-driver)). Use the memory driver with a fake clock, or `RunAll`, when the test must run the steps ([Choose by kind of app](app-types.md#tests)).
- **If losing queued work on a crash or deploy is acceptable** (a cache warm-up, a best-effort notification, a CLI tool, local development), use memory.
- **If you have one server and want durability with nothing new to run**, use sqlstore on a SQLite file. Several processes on that machine can share it.
- **If you run several machines and already have Postgres or MySQL 8**, use sqlstore on it. Workers claim steps with `FOR UPDATE SKIP LOCKED`, a cron tick fires once across all of them, and a crashed worker's step is taken over when its lease expires ([`defaultLease`](ds:block?id=sql-defaultlease-qygq5sbe), 30 seconds; [Leases and crashed workers](../drivers/sqlstore.md#leases-and-crashed-workers)).
- **If a job must be enqueued if and only if your own transaction commits**, use sqlstore with [`EnqueueTx`](ds:block?id=sql-client-enqueuetx-8tdebvcq) when the queue is the same database, or the outbox in front of any driver otherwise ([Enqueue, EnqueueTx or the outbox](methods.md#enqueue-enqueuetx-or-the-outbox)).
- **If you already run Redis and need durable jobs, cron and workflows**, use the redis driver: runs are claimed whole under a lease, writes are fenced, a tick fires once across clients, and it has everything the SQL driver has except closures, a cluster-wide queue limit, `Step.Slots` and transactional enqueue ([`redis` caps](ds:block?id=redis-caps-bfgdst9t)) ([The Redis driver](../drivers/redis.md#what-it-can-do-and-what-it-refuses)).
- **If you already run Hatchet, or want its dashboard and engine-side scheduling**, use the hatchet driver. Write concurrency and rate-limit keys as CEL ([`workflow.KeyExpr`](ds:block?id=keyexpr-gvanv9aq)), keep crons in UTC ([`checkSupported`](ds:block?id=hatchet-checksupported-733uwgsp)), and read [What Hatchet refuses](#what-hatchet-refuses) before you rely on a retry or schedule option.
- **If you start on one and expect to move**, write against `workflow.Client` only, keep keys as Go functions unless you are on Hatchet, run your workflows through a `FakeLike` test for each target driver, and move with a [cutover](#hybrid-failover-regional-cutover-or-pools) when the day comes.

## Hybrid, failover, regional, cutover or pools

Four wrappers take two or more clients and are themselves a `workflow.Client`, so app code does not change; pools are step middleware that limit a resource across every worker. Each wrapper owns its inner clients: it registers the workflows on them and starts them. Failover, regional and cutover refs carry a prefix that names the inner client (`primary:`, `eu:`, `new:`); hybrid hands out the jobs client's own refs.

| Option | Use it for | What it does | Capabilities it declares | Guide | Example |
|---|---|---|---|---|---|
| [`hybrid.New(scheduler, jobs)`](ds:block?id=hybrid-new-2d822hfp) | Crons in the app's process, jobs on a durable driver | Schedules fire on `scheduler` as one-step forwarders that enqueue the real job on `jobs` with an idempotency key `hybrid/<schedule>/<tick>`; everything else goes to `jobs` | The jobs client's, with the schedule family taken from the scheduler ([`scheduleCaps`](ds:block?id=hybrid-schedulecaps-zx4gtwq7), [`Capabilities`](ds:block?id=hybrid-client-capabilities-bvkxrkrc)); never `CapOverlapSkip`, `CapScheduleKeep`, `CapScheduleHistory`, `CapScheduleTrigger` or `CapTickEvents` | [Hybrid placement](../drivers/hybrid.md#split-schedules-from-runs) | [hybrid-placement](../../examples/hybrid-placement/) |
| [`failover.New(primary, secondary)`](ds:block?id=failover-new-r9uzm3cq) | An enqueue path that keeps working while one backend is down | `Enqueue` goes to the primary, and to the secondary when the classifier calls the primary's error an outage; runs never move | The intersection of both; the schedule family is the primary's alone unless `WithSchedulesOnBoth`; `CapClosure` and `CapWorkerScale` are the primary's ([`Capabilities`](ds:block?id=failover-client-capabilities-cb8n9pqm)) | [Failover](../reliability/failover.md#fail-over-to-a-second-backend) | [failover](../../examples/failover/), [failover-observer](../../examples/failover-observer/) |
| [`regional.New(regions, router)`](ds:block?id=regional-new-wmsu8tng) | Data residency: EU customers' runs in the EU, US in the US | A `Router` picks each job's region; a job never moves to another region, not even when its region is down | The intersection of every region's ([`Capabilities`](ds:block?id=regional-client-capabilities-858xwx63)); never `CapClosure` or `CapWorkerScale` ([`excludedCaps`](ds:block?id=regional-excludedcaps-vuc7vjgy)) | [Regional routing](../operations/regional-routing.md#route-each-job-to-its-region) | [regional-routing](../../examples/regional-routing/) |
| [`cutover.New(old, new)`](ds:block?id=cutover-new-wkttdfys) | Moving to another backend without a stop (SQLite to Postgres, SQL to Hatchet) | New work goes to `new`, `old` finishes what it holds, `Remaining` says when it is empty, `MoveSchedules` moves run-time schedules | The new backend's for the enqueue path, both backends' for the run family, the schedule backend's for schedules; never trigger-now, tick events, worker scaling, closures, force or drain reports ([`Capabilities`](ds:block?id=cutover-client-capabilities-sq86kg5y)) | [Backend cutover](../operations/cutover.md#join-the-two-backends) | [backend-cutover](../../examples/backend-cutover/) |
| [`middleware.Pool`](ds:block?id=mw-pool-qwknhvvp), `CriticalSection`, `AutoDisable` | A resource with N seats shared by every workflow (GPUs, licences, a partner's connection cap), two steps of one run that must take turns, an endpoint that keeps failing | Step middleware over a `UniqueStore` or `DisableStore`; a step that finds no free slot snoozes | Pools snooze, so they need `CapSnooze` (memory, sqlstore, Redis); on Hatchet use [`PoolRetryAfter()`](ds:block?id=mw-poolretryafter-xtdeqgqp), which spends an attempt | [Pools, critical sections and auto-disable](../reliability/pools.md#share-a-pool-of-slots) | [job-guards](../../examples/job-guards/) |

### If X, then Y for wrappers

- **If crons belong in the app's code and jobs must survive a restart**, use [`hybrid.New(memory.New(), durable)`](ds:block?id=hybrid-new-2d822hfp). With one node, or with every node firing and the idempotency key folding the duplicates, it needs nothing else; for a tick that must fire once per cluster, schedule on the durable driver itself.
- **If the risk is an outage of the whole backend** (the Hatchet engine, a managed Postgres) and accepting work matters more than where it runs, use failover. Put an `IdempotencyKey` on every job: without one `Enqueue` returns [`failover.ErrKeyRequired`](ds:block?id=failover-errkeyrequired-5ywe568r), because a primary that accepted a job and then failed to answer would make failover run it twice. [`AllowWithoutKey`](ds:block?id=failover-allowwithoutkey-4fzbzhje) accepts that risk.
- **If the rule is legal (a customer's data stays in its region)**, use regional. For an outage inside one region, make that region's client a failover client of two backends in the same region, never a second region.
- **If you are moving from one backend to another**, use cutover for the weeks the old one still holds runs, then deploy with the new client alone once `Remaining` is zero and the schedules have moved.
- **If several workflows share a scarce resource**, use a [pool](ds:block?id=mw-pool-qwknhvvp) with a shared store ([`sqlstore.UniqueStore`](ds:block?id=sql-client-uniquestore-k86jhwu9) or the Redis one). If only runs of one workflow with the same key compete, a [concurrency key](methods.md#concurrency-limit-or-rate-limit) is simpler.
- **If you combine them**, nest them: regional over one failover client per region, each over two drivers in that region. Signals addressed to a run (`SignalRun`) and `OnSignals` handlers reach the right inner client through regional, failover, cutover and hybrid ([Behind wrappers](../workflows/escalation.md#behind-wrappers)).

## Pitfalls

- The memory driver accepts a workflow that sleeps for a week: durability is never inferred from a workflow, so nothing refuses it. Choosing memory is choosing to lose that sleep on exit.
- The Redis driver refuses closures (`EnqueueClosure`), expression keys (`KeyExpr`; [`exprKeys`](ds:block?id=redis-exprkeys-g3qq6r7w)), a non-zero `QueueConfig.Limit` and `Step.Slots` above 1 ([`redis` caps](ds:block?id=redis-caps-bfgdst9t), [`Register`](ds:block?id=redis-client-register-zy9gzzxh)), and cannot enqueue inside your SQL transaction; use functions by name, Go key functions and the outbox there.
- SQLite is durable on one machine, not shared across machines. A network file system does not change that.
- [`sqlstore.New`](ds:block?id=sql-new-89qpbdvm) never creates tables, and [`Start`](ds:block?id=sql-client-start-ab8ayzsy) never migrates: run [`Client.Migrate`](ds:block?id=sql-client-migrate-vdt8uy3d) from your deploy first ([Run the migrations](../operations/migrations.md#run-the-migrations)).
- Every sqlstore client sharing a database must use the same cron parser; a different table prefix is a different, separate queue ([Namespaces](../operations/namespaces.md#one-namespace-per-client)).
- On Hatchet, `OnRunFinished` is best effort (no `CapRunFinished` in its [caps](ds:block?id=hatchet-caps-d6x9fv8z)): a restarted client replays only ends of runs created within [`Config.RunFinishedCatchUp`](ds:block?id=hatchet-config-wdky3m9f). Features that rely on run ends (`UniqueUntilFinished`, batch callbacks) keep their fallback there: a TTL, a poller or Hatchet's own `BatchSource`.
- Concurrency and rate-limit keys written as Go functions are refused by Hatchet at `Register` ([`checkSupported`](ds:block?id=hatchet-checksupported-733uwgsp)), and CEL expressions are refused by memory, sqlstore and Redis at `Start` ([`memory`](ds:block?id=memory-exprkeys-mrxv22pq), [`sqlstore`](ds:block?id=sql-exprkeys-wxvw57q3), [`redis`](ds:block?id=redis-exprkeys-g3qq6r7w)). Wait keys are the other way round on Hatchet: it refuses `KeyExpr` there and takes `KeyFunc`. Moving between drivers means rewriting concurrency and rate keys only. Hatchet also refuses a rate limit with no key; use `KeyExpr("\"all\"")` for one bucket.
- A wrapper refuses an optional call (run listing, retry, pause) when any inner client it would need lacks it, rather than answering from one side, because the answer would silently miss runs. Check [`workflow.Supports(c, op)`](ds:block?id=supports-4xyjjwvz) or the capability on the wrapper itself, not on one inner client.
- Never use a failover, regional or cutover client's inner clients directly for app work: their refs have no prefix, and the wrapper answers `workflow.ErrNotFound` for them.
- Hybrid refuses `OverlapSkip` and `KeepRuns` (the scheduler sees only its forwarder runs) and `TriggerSchedule` ([`scheduleCaps`](ds:block?id=hybrid-schedulecaps-zx4gtwq7)); a run-time `Schedule` on a memory scheduler is lost on restart. Declare recurring work as `Workflow.Cron` there.
- Failover with [`WithSchedulesOnBoth`](ds:block?id=failover-withschedulesonboth-vp7d75qm) fires every tick twice while both backends are up; without it, schedules stop while the primary is down.
