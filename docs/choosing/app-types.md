# Choose by kind of app

A starting set of driver, options and middleware for the kinds of app that use a job library, with the reason for each pick. Each row is a default, not a rule: the [driver guide](drivers.md), the [method guide](methods.md) and the [schedule](schedules.md) and [operations](operations.md) guides explain the trade-offs behind it.

## The table

| Kind of app | Driver | Turn on | Leave off, and why | Guides | Example |
|---|---|---|---|---|---|
| A web app or API on one server | `sqlstore` on a SQLite file | `Migrate` at deploy, `EnqueueTx` for jobs tied to your writes, retries with `Permanent` for bad input, `WithRetention`, `middleware.Logging` and `Recover` | Failover: one machine is one failure domain either way | [SQL driver](../drivers/sqlstore.md#create-the-client), [transactional enqueue](../reliability/transactional-enqueue.md#enqueue-inside-your-transaction), [retention](../operations/retention.md#keep-finished-runs-for-a-while) | [sqlite-worker](../../examples/sqlite-worker/) |
| A web fleet with separate worker processes | `sqlstore` on Postgres or MySQL 8, or `redis` | Web nodes built `WithEnqueueOnly()` (no `Start`, no polling, no cron), workers that register the same workflows, `pgnotify` to wake them at once on Postgres, `Workflow.Version` for rolling deploys, a drain with a grace period on SIGTERM, `/livez` and `/readyz` from `CheckHealth` | Workers on the web nodes: they compete with requests; run-finished observers on enqueue-only nodes, which never deliver run ends | [web nodes that only enqueue](../operations/deploy.md#web-nodes-that-only-enqueue), [rolling deploys](../operations/deploy.md#deploy-a-new-version-while-old-workers-run), [shut down cleanly](../operations/deploy.md#shut-down-cleanly), [probes](../operations/nodes.md#health-and-readiness-probes) | [enqueue-only](../../examples/enqueue-only/), [worker-wakeup](../../examples/worker-wakeup/), [rolling-deploy](../../examples/rolling-deploy/), [node-health](../../examples/node-health/) |
| A multi-tenant SaaS on several machines | `sqlstore` on Postgres or MySQL 8, or `redis` | `Job.Tenant` and `Schedule.Tenant` on every enqueue, `Workflow.Concurrency` keyed by tenant with `ConcurrencyRoundRobin` (and `Weight` for paid tiers) so one tenant cannot starve the rest, `UniqueUntilFinished` with a shared store for one sync per account, `Client.Schedule` per tenant, `admin.WithTenantScope` for a customer-facing runs page, the `otel` module | The memory stores (`MemoryUnique`, `MemoryDebounce`): each process would keep its own | [tenants](../jobs/tenants.md#enqueue-a-job-for-a-tenant), [fair turns between keys](../jobs/concurrency.md#share-the-workers-fairly-between-keys), [unique jobs](../reliability/unique-jobs.md#a-store-shared-by-every-process), [per-tenant dashboard](../admin/tenants.md#step-1-say-which-tenant-each-caller-sees) | [postgres-cluster](../../examples/postgres-cluster/), [fair-share](../../examples/fair-share/), [admin-tenants](../../examples/admin-tenants/) |
| Staging and production on shared infrastructure | the same driver | A table prefix (SQL) or key prefix (Redis) per environment, read from one config value | One prefix for both: they would share every run, schedule, pause and unique lock | [namespaces](../operations/namespaces.md#step-1--give-each-sql-namespace-a-table-prefix) | [namespaces](../../examples/namespaces/) |
| A multi-region app with data residency | `regional.New` over one client per region (each a durable driver, or a failover client of two backends inside the region) | A `Router` (`regional.ByLabel`, or one of your own: by tenant, by a customer lookup), `WithScheduleRegion` for declared crons, `WithSignalRouter` so an event's payload stays in one region | Moving a job to another region during an outage: regional never does, by design | [regional routing](../operations/regional-routing.md#route-each-job-to-its-region) | [regional-routing](../../examples/regional-routing/) |
| A team already running Hatchet | `hatchet` | CEL keys (`workflow.KeyExpr`), batches as native groups, `hatchet.Client.BatchSource`, the outbox if jobs must match your own database's commits, the run recorder with its `Reconciler` for history | Misfire policies, retry jitter, `DelayFor`, chains, versions and non-UTC crons: the driver refuses them; snoozes spend attempts there; anything that needs every run end guaranteed | [Hatchet driver](../drivers/hatchet.md#what-it-can-do-and-what-it-refuses), [native groups](../batches/native-groups.md#native-group-runs), [outbox](../reliability/outbox.md#write-jobs-inside-your-transaction) | [hatchet-worker](../../examples/hatchet-worker/) |
| A desktop app, CLI or agent on a laptop | `sqlstore` on SQLite for work that must survive a restart; `memory` for work that may not | Durable sleeps and waits (a reminder in three days), `Misfire{Policy: MisfireFireOnce}` so a laptop that slept runs the missed tick once, `clock.WakeChecked` on the memory driver | Several worker processes on different machines: SQLite shares one machine | [sleep](../workflows/sleep.md#sleep-inside-a-workflow), [misfire policies](../schedules/misfire.md#misfire-policies), [laptops that sleep](../operations/sleep-and-wake.md#wrap-the-clock) | [sqlite-worker](../../examples/sqlite-worker/), [sleep-wake](../../examples/sleep-wake/) |
| An edge device that boots with a wrong clock | `sqlstore` on SQLite | `workflow.StartWhen` with `ClockAfter(clk, buildTime)` in place of `Start`, a `ReadyFunc` that also waits for the network or the database | Scheduling before the clock is synchronised: every tick would be computed from 1970 | [start when ready](../operations/start-gate.md#step-1--hold-start-until-the-clock-is-synchronised) | [start-gate](../../examples/start-gate/) |
| Heavy fan-out: imports, mass email, report generation | `sqlstore` on Postgres, or `hatchet` | `batch` with `Then`, `Catch` and `Finally` and a durable store, `Workflow.RateLimits` for the downstream API, a [pool](../reliability/pools.md#share-a-pool-of-slots) for a resource shared across workflows, the claim check for big payloads | Plain loops of `Enqueue` when you need to know when the group is done | [batches](../batches/batches.md#dispatch-a-batch), [durable batches](../batches/durability.md#a-durable-store), [rate limits](../jobs/concurrency.md#rate-limits), [claim check](../reliability/claim-check.md#move-big-payloads-out-of-the-queue) | [batches](../../examples/batches/), [job-guards](../../examples/job-guards/) |
| Webhook receivers and payment flows | any durable driver | `Job.IdempotencyKey` from the provider's event ID, `IdempotencyRequired` on the workflow, wait steps for the reply (`Step.Wait` and `Client.Signal`), payload encryption | Debounce: every event matters | [idempotency keys](../jobs/idempotency.md#idempotency-keys), [wait for an event](../workflows/signals.md#wait-for-an-event), [encrypt payloads](../middleware/codecs.md#encrypt-payloads) | [idempotency](../../examples/idempotency/), [signals-and-sleep](../../examples/signals-and-sleep/) |
| An enqueue path that must keep working through a backend outage | `failover.New(primary, secondary)` over two drivers | Idempotency keys on every job (required), `WithCoolOff`, `WithObserver` to alert | Schedules on both backends unless you want them to fire twice (`WithSchedulesOnBoth` is opt-in) | [failover](../reliability/failover.md#fail-over-to-a-second-backend) | [failover](../../examples/failover/) |
| An app moving to another backend | `cutover.New(old, new)` for the weeks of the move | `Remaining` to know when the old backend is empty, `MoveSchedules` for run-time schedules | Enqueueing on the old backend: cutover never does, and it does not fail over | [backend cutover](../operations/cutover.md#join-the-two-backends) | [backend-cutover](../../examples/backend-cutover/) |
| App tests | `workflowtest.Fake` built with `FakeLike(prodClient)` | Its assertions (`AssertEnqueued`, `AssertScheduled`, ...); `memory` with a fake clock or `RunAll` when steps must run | Real time in tests: a test that waits for a backoff is slow and flaky | [the Fake](../testing/fake.md#behave-like-your-production-driver), [fake clock](../testing/fake-clock.md#drive-time-in-tests) | [app-tests](../../examples/app-tests/) |
| A library or framework that offers background jobs | depend on `workflow.Client` only | A `workflow.Plugin` for your rules, the conformance suite for any driver you ship | Choosing a driver for your users | [write a plugin](../extending/writing-a-plugin.md#write-a-plugin), [write a driver](../extending/writing-a-driver.md#run-the-conformance-suite) | [custom-plugin](../../examples/custom-plugin/), [custom-driver](../../examples/custom-driver/) |

## Tests

Pick by what the test must prove: what your code asked for, what one step does, or what a whole workflow does over time.

| Tool | Proves | Runs steps | Guide | Example |
|---|---|---|---|---|
| `workflowtest.NewFake(workflowtest.FakeLike(prod))` | What app code enqueued, signalled, scheduled, paused or retried; refuses what the production driver would | no | [Behave like your production driver](../testing/fake.md#behave-like-your-production-driver) | [app-tests](../../examples/app-tests/) |
| The Fake's batch, chain and operations assertions | That code dispatched a batch, built a chain, sent a job to a queue with a retry budget | no | [Test batches, chains and a subset of workflows](../testing/batches-and-chains.md), [Test queues, retries and pauses](../testing/operations.md) | [batch-tests](../../examples/batch-tests/) |
| `workflowtest.RunStep(handler, in, opts...)` | How one handler's attempt ends: success, retry, `RetryAfter`, `Permanent`, `Discard` | one handler, no client | [Test one step](../testing/run-step.md#step-1-run-the-handler-and-check-the-outcome) | [batch-tests](../../examples/batch-tests/) |
| `workflowtest.NewRecorder(inner)` | What was enqueued, while the jobs really run on `inner` | yes | [Record a real client](../testing/recorder.md#record-a-real-client) | [app-tests](../../examples/app-tests/) |
| `memory.New(memory.WithClock(clock.NewFake(t0)))` | Timing: a reminder in a day, a retry in ten minutes, a cron tick, stepped on cue | yes | [Drive time in tests](../testing/fake-clock.md#drive-time-in-tests) | [app-tests](../../examples/app-tests/) |
| `memory.Client.RunAll(ctx)` | That everything enqueued ends, and how, without stepping a clock: delays, backoffs, snoozes and sleeps end at once | yes | [Run everything now](../testing/run-all.md#run-everything-now) | [run-all](../../examples/run-all/) |
| `workflow.RunInline(ctx, wf, job)` | A whole workflow's result in the test's goroutine, with no driver | yes | [Run a workflow inline](../jobs/run-inline.md#step-1-run-it) | [run-inline](../../examples/run-inline/) |
| `workflowtest.Run(t, harness)` | That a driver you wrote honours every capability it declares | yes | [Run the conformance suite](../extending/writing-a-driver.md#run-the-conformance-suite) | [driver-conformance](../../examples/driver-conformance/) |

## If X, then Y

- If your API runs somewhere that cannot keep goroutines alive (a function platform), run the workers as a separate long-lived process on the same driver. The API side only enqueues: `Enqueue` and `EnqueueTx` need a started client unless it is built enqueue-only, and `outbox.Outbox.Write` needs only a database transaction, with the relay running beside the workers.
- If one tenant's spike must not delay the others, key concurrency (or rate limits) by tenant: each tenant gets its own `MaxRuns`, and `ConcurrencyRoundRobin` makes the waiting tenants take turns ([Strategies](../jobs/concurrency.md#strategies)). `Job.Tenant` alone limits nothing.
- If customers may see their own runs, mount the admin API with `admin.WithTenantScope`; the handler enforces the scope on every route.
- If workers should scale to zero while crons keep firing, run one small node `WithSchedulerOnly()` and the workers `WithoutScheduler()` ([Choose a schedule tool](schedules.md#who-fires-a-tick-the-tick-row-leader-election-or-a-scheduler-node)).
- If a job carries personal data, seal it with the codec `middleware.Encrypt(key, oldKeys...)` returns, applied with `middleware.WithCodec`; the old keys still decrypt during rotation. In a multi-region app, also route its signals with `WithSignalRouter`.
- If a payload can be megabytes, move it out of the queue with the claim check rather than raising database or engine limits.
- If support or operations staff need a runs page that says who started each run, what each step did and whether the work went well, add the [run recorder](../observability/run-recorder.md) with `sqlrecorder` in your database: `RequireSource` on the enqueue path, `EnqueuePlugin` on web nodes that only enqueue, `Plugin` on the workers, and on Hatchet the `Reconciler` ([Choose an operations tool](operations.md#archive-tables-the-witharchive-hook-or-the-run-recorder)).
- If you are not sure which you are, start with `sqlstore` on SQLite: it is durable, needs nothing new, and moving to Postgres later changes the dialect and the DSN.

## Pitfalls

- A web app and its worker processes must register the same workflows: `Enqueue` refuses a workflow the calling client has not registered (`ErrNotFound`). An enqueue-only client accepts an unregistered workflow but stamps version 0 on it, so register versioned workflows on web nodes too.
- `EnqueueTx` needs the job's workflow registered on that client and the client started (or built enqueue-only), like `Enqueue`.
- An enqueue-only client never delivers run ends: register run-finished observers (alerts, reporters, unique-lock release) on the workers.
- A run recorder on a web node built enqueue-only needs `rec.EnqueuePlugin()`: Hatchet's enqueue-only client refuses the full plugin, and the SQL and Redis ones deliver no run ends ([Web nodes that only enqueue](../observability/run-recorder.md#web-nodes-that-only-enqueue)).
- On Hatchet, a plugin or feature that needs every run end (batch callbacks through the hook alone, `UniqueUntilFinished` without its TTL) needs the fallback the library already adds there: a status poller or the TTL.
- With several regions, a workflow with a declared `Cron` needs `WithScheduleRegion`, and its ticks run in that region only.
- A tenant is a field, not a boundary: it does not stop one tenant's code from reading another's data, and it does not limit a tenant's share of the workers.
- A `StartWhen` gate whose check never passes keeps the client stopped with no error; give the `ReadyFunc` its own deadline.
- The Fake runs nothing, so a test on it never proves a handler works; pair it with `RunStep` or a memory-driver test for the handlers themselves.
