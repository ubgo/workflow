# Choose by kind of app

A starting set of driver, options and middleware for the kinds of app that use a job library, with the reason for each pick. Each row is a default, not a rule: the [driver guide](drivers.md), the [method guide](methods.md) and the [schedule](schedules.md) and [operations](operations.md) guides explain the trade-offs behind it.

## The table

| Kind of app | Driver | Turn on | Leave off, and why | Guides | Example |
|---|---|---|---|---|---|
| A web app or API on one server | `sqlstore` on a SQLite file | [`Migrate`](ds:block?id=sql-client-migrate-vdt8uy3d) at deploy, [`EnqueueTx`](ds:block?id=sql-client-enqueuetx-8tdebvcq) for jobs tied to your writes, retries with [`Permanent`](ds:block?id=permanent-9e6vjm6s) for bad input, [`WithRetention`](ds:block?id=sql-withretention-dk86xzbt), [`middleware.Logging`](ds:block?id=mw-logging-zanq5b67) and [`Recover`](ds:block?id=mw-recover-a7qbjc9u) | Failover: one machine is one failure domain either way | [SQL driver](../drivers/sqlstore.md#create-the-client), [transactional enqueue](../reliability/transactional-enqueue.md#enqueue-inside-your-transaction), [retention](../operations/retention.md#keep-finished-runs-for-a-while) | [sqlite-worker](../../examples/sqlite-worker/) |
| A web fleet with separate worker processes | `sqlstore` on Postgres or MySQL 8, or `redis` | Web nodes built [`WithEnqueueOnly()`](ds:block?id=sql-withenqueueonly-z8xgtkdr) (no `Start`, no polling, no cron), workers that register the same workflows, `pgnotify` to wake them at once on Postgres, `Workflow.Version` for rolling deploys, a drain with a grace period on SIGTERM, `/livez` and `/readyz` from [`CheckHealth`](ds:block?id=checkhealth-6rntx5kf) | Workers on the web nodes: they compete with requests; run-finished observers on enqueue-only nodes, which never deliver run ends | [web nodes that only enqueue](../operations/deploy.md#web-nodes-that-only-enqueue), [rolling deploys](../operations/deploy.md#deploy-a-new-version-while-old-workers-run), [shut down cleanly](../operations/deploy.md#shut-down-cleanly), [probes](../operations/nodes.md#health-and-readiness-probes) | [enqueue-only](../../examples/enqueue-only/), [worker-wakeup](../../examples/worker-wakeup/), [rolling-deploy](../../examples/rolling-deploy/), [node-health](../../examples/node-health/) |

| Staging and production on shared infrastructure | the same driver | A table prefix (SQL) or key prefix (Redis) per environment, read from one config value | One prefix for both: they would share every run, schedule, pause and unique lock | [namespaces](../operations/namespaces.md#step-1--give-each-sql-namespace-a-table-prefix) | [namespaces](../../examples/namespaces/) |
| A multi-region app with data residency | [`regional.New`](ds:block?id=regional-new-wmsu8tng) over one client per region (each a durable driver, or a failover client of two backends inside the region) | A `Router` ([`regional.ByLabel`](ds:block?id=regional-bylabel-8wqynpjc), or one of your own: by tenant, by a customer lookup), [`WithScheduleRegion`](ds:block?id=regional-withscheduleregion-hkwwqse4) for declared crons, [`WithSignalRouter`](ds:block?id=regional-withsignalrouter-jjp6ts9d) so an event's payload stays in one region | Moving a job to another region during an outage: regional never does, by design | [regional routing](../operations/regional-routing.md#route-each-job-to-its-region) | [regional-routing](../../examples/regional-routing/) |
| A team already running Hatchet | `hatchet` | CEL keys ([`workflow.KeyExpr`](ds:block?id=keyexpr-gvanv9aq)), batches as native groups, [`hatchet.Client.BatchSource`](ds:block?id=hatchet-client-batchsource-prb3q7d4), the outbox if jobs must match your own database's commits, the run recorder with its `Reconciler` for history | Misfire policies, retry jitter, `DelayFor`, chains, versions and non-UTC crons: the driver refuses them ([`checkSupported`](ds:block?id=hatchet-checksupported-733uwgsp), [caps](ds:block?id=hatchet-caps-d6x9fv8z)); snoozes spend attempts there; anything that needs every run end guaranteed | [Hatchet driver](../drivers/hatchet.md#what-it-can-do-and-what-it-refuses), [native groups](../batches/native-groups.md#native-group-runs), [outbox](../reliability/outbox.md#write-jobs-inside-your-transaction) | [hatchet-worker](../../examples/hatchet-worker/) |
| A desktop app, CLI or agent on a laptop | `sqlstore` on SQLite for work that must survive a restart; `memory` for work that may not | Durable sleeps and waits (a reminder in three days), [`Misfire{Policy: MisfireFireOnce}`](ds:block?id=misfire-hwbgv2py) so a laptop that slept runs the missed tick once, [`clock.WakeChecked`](ds:block?id=clock-wakechecked-pdvq4r34) on the memory driver | Several worker processes on different machines: SQLite shares one machine | [sleep](../workflows/sleep.md#sleep-inside-a-workflow), [misfire policies](../schedules/misfire.md#misfire-policies), [laptops that sleep](../operations/sleep-and-wake.md#wrap-the-clock) | [sqlite-worker](../../examples/sqlite-worker/), [sleep-wake](../../examples/sleep-wake/) |
| An edge device that boots with a wrong clock | `sqlstore` on SQLite | [`workflow.StartWhen`](ds:block?id=startwhen-rgx6keu2) with [`ClockAfter(clk, buildTime)`](ds:block?id=clockafter-3nzw3qf4) in place of `Start`, a `ReadyFunc` that also waits for the network or the database | Scheduling before the clock is synchronised: every tick would be computed from 1970 | [start when ready](../operations/start-gate.md#step-1--hold-start-until-the-clock-is-synchronised) | [start-gate](../../examples/start-gate/) |

| Webhook receivers and payment flows | any durable driver | [`Job.IdempotencyKey`](ds:block?id=job-j5g728nc) from the provider's event ID, [`IdempotencyRequired`](ds:block?id=idempotencyrequired-g889m7p8) on the workflow, wait steps for the reply (`Step.Wait` and `Client.Signal`), payload encryption | Debounce: every event matters | [idempotency keys](../jobs/idempotency.md#idempotency-keys), [wait for an event](../workflows/signals.md#wait-for-an-event), [encrypt payloads](../middleware/codecs.md#encrypt-payloads) | [idempotency](../../examples/idempotency/), [signals-and-sleep](../../examples/signals-and-sleep/) |

## Tests

Pick by what the test must prove: what your code asked for, what one step does, or what a whole workflow does over time.

| Tool | Proves | Runs steps | Guide | Example |
|---|---|---|---|---|
| [`workflowtest.NewFake(workflowtest.FakeLike(prod))`](ds:block?id=workflowtest-fakelike-my3v73nf) | What app code enqueued, signalled, scheduled, paused or retried; refuses what the production driver would | no | [Behave like your production driver](../testing/fake.md#behave-like-your-production-driver) | [app-tests](../../examples/app-tests/) |
| The Fake's batch, chain and operations assertions | That code dispatched a batch, built a chain, sent a job to a queue with a retry budget | no | [Test batches, chains and a subset of workflows](../testing/batches-and-chains.md), [Test queues, retries and pauses](../testing/operations.md) | [batch-tests](../../examples/batch-tests/) |
| [`workflowtest.RunStep(handler, in, opts...)`](ds:block?id=workflowtest-runstep-zsng78k5) | How one handler's attempt ends: success, retry, `RetryAfter`, `Permanent`, `Discard` | one handler, no client | [Test one step](../testing/run-step.md#step-1-run-the-handler-and-check-the-outcome) | [batch-tests](../../examples/batch-tests/) |
| [`workflowtest.NewRecorder(inner)`](ds:block?id=workflowtest-newrecorder-r3wxkycy) | What was enqueued, while the jobs really run on `inner` | yes | [Record a real client](../testing/recorder.md#record-a-real-client) | [app-tests](../../examples/app-tests/) |
| [`memory.New(memory.WithClock(clock.NewFake(t0)))`](ds:block?id=clock-newfake-3fjcs7pm) | Timing: a reminder in a day, a retry in ten minutes, a cron tick, stepped on cue | yes | [Drive time in tests](../testing/fake-clock.md#drive-time-in-tests) | [app-tests](../../examples/app-tests/) |
| [`memory.Client.RunAll(ctx)`](ds:block?id=memory-client-runall-zdkrjb96) | That everything enqueued ends, and how (each run's `Status`; the report's counts leave out runs that ended before the call: [Count only what the report covers](../testing/run-all.md#count-only-what-the-report-covers)), without stepping a clock: delays, backoffs, snoozes and sleeps end at once | yes | [Run everything now](../testing/run-all.md#run-everything-now) | [run-all](../../examples/run-all/) |
| [`workflow.RunInline(ctx, wf, job)`](ds:block?id=runinline-c8wjejut) | A whole workflow's result in the test's goroutine, with no driver | yes | [Run a workflow inline](../jobs/run-inline.md#step-1-run-it) | [run-inline](../../examples/run-inline/) |

## If X, then Y

- If your API runs somewhere that cannot keep goroutines alive (a function platform), run the workers as a separate long-lived process on the same driver. The API side only enqueues: `Enqueue` and `EnqueueTx` need a started client unless it is built enqueue-only, and [`outbox.Outbox.Write`](ds:block?id=outbox-outbox-write-pxkp6pag) needs only a database transaction, with the relay running beside the workers.
- If one tenant's spike must not delay the others, key concurrency (or rate limits) by tenant: each tenant gets its own `MaxRuns`, and [`ConcurrencyRoundRobin`](ds:block?id=concurrencyroundrobin-rd8zthfc) makes the waiting tenants take turns ([Strategies](../jobs/concurrency.md#strategies)). `Job.Tenant` alone limits nothing.
- If customers may see their own runs, mount the admin API with [`admin.WithTenantScope`](ds:block?id=admin-withtenantscope-cbtmkxnu); the handler enforces the scope on every route.
- If workers should scale to zero while crons keep firing, run one small node [`WithSchedulerOnly()`](ds:block?id=sql-withscheduleronly-af8r5q7m) and the workers [`WithoutScheduler()`](ds:block?id=sql-withoutscheduler-nbbxc2s8) ([Choose a schedule tool](schedules.md#who-fires-a-tick-the-tick-row-leader-election-or-a-scheduler-node)).
- If a job carries personal data, seal it with the codec [`middleware.Encrypt(key, oldKeys...)`](ds:block?id=mw-encrypt-m3ndvkk8) returns, applied with [`middleware.WithCodec`](ds:block?id=mw-withcodec-4aa2ymdy); the old keys still decrypt during rotation. In a multi-region app, also route its signals with `WithSignalRouter`.
- If a payload can be megabytes, move it out of the queue with the claim check rather than raising database or engine limits.
- If support or operations staff need a runs page that says who started each run, what each step did and whether the work went well, add the [run recorder](../observability/run-recorder.md) with `sqlrecorder` in your database: `RequireSource` on the enqueue path, [`EnqueuePlugin`](ds:block?id=rec-recorder-enqueueplugin-rn5k8npv) on web nodes that only enqueue, [`Plugin`](ds:block?id=rec-recorder-plugin-u7hfc2yc) on the workers, and on Hatchet the [`Reconciler`](ds:block?id=rec-reconciler-55m8wpc9) ([Choose an operations tool](operations.md#archive-tables-the-witharchive-hook-or-the-run-recorder)).
- If you are not sure which you are, start with `sqlstore` on SQLite: it is durable, needs nothing new, and moving to Postgres later changes the dialect and the DSN.

## Pitfalls

- A web app and its worker processes must register the same workflows: `Enqueue` refuses a workflow the calling client has not registered (`ErrNotFound`). An enqueue-only client accepts an unregistered workflow but stamps version 0 on it ([`enqueueReg`](ds:block?id=sql-client-enqueuereg-pzaxh9eg) on sqlstore), so register versioned workflows on web nodes too.
- [`EnqueueTx`](ds:block?id=sql-client-enqueuetx-8tdebvcq) needs the job's workflow registered on that client and the client started (or built enqueue-only), like `Enqueue`.
- An enqueue-only client never delivers run ends: register run-finished observers (alerts, reporters, unique-lock release) on the workers.
- A run recorder on a web node built enqueue-only needs [`rec.EnqueuePlugin()`](ds:block?id=rec-recorder-enqueueplugin-rn5k8npv): Hatchet's enqueue-only client refuses the full plugin, and the SQL and Redis ones deliver no run ends ([Web nodes that only enqueue](../observability/run-recorder.md#web-nodes-that-only-enqueue)).
- On Hatchet, a plugin or feature that needs every run end (batch callbacks through the hook alone, `UniqueUntilFinished` without its TTL) needs the fallback the library already adds there: a status poller or the TTL.
- With several regions, a workflow with a declared `Cron` needs [`WithScheduleRegion`](ds:block?id=regional-withscheduleregion-hkwwqse4), and its ticks run in that region only.
- A tenant is a field, not a boundary: it does not stop one tenant's code from reading another's data, and it does not limit a tenant's share of the workers.
- A [`StartWhen`](ds:block?id=startwhen-rgx6keu2) gate whose check never passes keeps the client stopped with no error; give the `ReadyFunc` its own deadline.
- The Fake runs nothing, so a test on it never proves a handler works; pair it with [`RunStep`](ds:block?id=workflowtest-runstep-zsng78k5) or a memory-driver test for the handlers themselves.
