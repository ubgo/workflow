# Names

Every name the library reserves or writes on your behalf: the job labels its packages stamp, the tables and migration owners in your database, the metadata keys on a Hatchet run, the IDs it generates, and the span, attribute and metric names it exports. Keep app names out of these spaces; where a collision would break something, the library refuses it with an error rather than overwriting or dropping your value.

[`workflow.ReservedLabelPrefixes()`](ds:block?id=reservedlabelprefixes-s6pnbs6s) returns the three as a fresh slice, [`workflow.ReservedLabel(key)`](ds:block?id=reservedlabel-be47d7qr) says whether a key falls under one and which, and [`workflow.ValidateLabels(labels)`](ds:block?id=validatelabels-henfu882) refuses app labels under any of them with [`workflow.ErrInvalid`](ds:block?id=errinvalid-y3xxpcy2). [`ValidateSchedule`](ds:block?id=validateschedule-knj437ed) calls it, and each owning package refuses incoming labels under its own prefix, so an app label can never be mistaken for one the library wrote. Every driver's public `Enqueue` (and `EnqueueTx`, `EnqueueMany` and group dispatch) calls [`workflow.CheckJobLabels(ctx, job)`](ds:block?id=checkjoblabels-p6m28b9h), which refuses a reserved label on a job or a chained job with [`workflow.ErrInvalid`](ds:block?id=errinvalid-y3xxpcy2) unless the package that owns it allowed it on the context (`workflow.AllowReservedLabels`, `AllowReservedPrefix`); internal paths (a fired schedule, a chained job, a retry) carry labels the library wrote and are not checked. It guards against a reserved label typed by an app or copied from a request, not against code in the same process that calls the allow functions itself.

The Hatchet driver stores labels as the run's additional metadata, beside keys of its own and of Hatchet's. A label that would shadow one of them is refused with an `UnsupportedError` on `Job.Labels` ([`runMetadata`](ds:block?id=hatchet-runmetadata-hrnkbdru)):

| Reserved by | Keys |
|---|---|
| The Hatchet driver | Every key starting `wf__` ([`metadataPrefix`](ds:block?id=hatchet-metadataprefix-2ytt6uuf)): `wf__idempotency_key`, `wf__workflow`, `wf__schedule_token`, `wf__enqueued_at`, `wf__queue`, `wf__priority` |
| Hatchet and its SDK | Every key starting `hatchet__` ([`hatchetMetadataPrefix`](ds:block?id=hatchet-hatchetmetadataprefix-hsdu59q6)), and `traceparent` ([`traceparentKey`](ds:block?id=hatchet-traceparentkey-646qsgud)) |

## Metrics

The `otel` package records under the instrumentation scope `github.com/ubgo/workflow/otel` ([`otel.ScopeName`](ds:block?id=otel-scopename-5xfp7mp2)). The Guide column links the section that turns each one on.

| Metric | Constant | Type and unit | What it counts | Guide |
|---|---|---|---|---|
| `workflow.step.duration` | [`otel.MetricStepDuration`](ds:block?id=otel-metricstepduration-hedu2w5b) | Histogram, `s` | The duration of each step attempt | [Metrics](../observability/opentelemetry.md#metrics) |
| `workflow.step.outcomes` | [`otel.MetricStepOutcomes`](ds:block?id=otel-metricstepoutcomes-hxy5z37a) | Counter, `{attempt}` | Step attempts by outcome | [Metrics](../observability/opentelemetry.md#metrics) |
| `workflow.enqueue.count` | [`otel.MetricEnqueueCount`](ds:block?id=otel-metricenqueuecount-xg9zbms4) | Counter, `{job}` | Enqueues by outcome | [Metrics](../observability/opentelemetry.md#metrics) |
| `workflow.queue.wait` | [`otel.MetricQueueWait`](ds:block?id=otel-metricqueuewait-cvnnku6c) | Histogram, `s` | How long each step attempt waited for a worker, from `StepInfo.ReadyAt` to its start (buckets [`otel.QueueWaitBuckets()`](ds:block?id=otel-queuewaitbuckets-m9t9px3s), 5 ms to 1 h); no sample when the driver sets no `ReadyAt` | [Queue wait and queue depth](../observability/opentelemetry.md#queue-wait-and-queue-depth) |
| `workflow.runs.finished` | [`otel.MetricRunsFinished`](ds:block?id=otel-metricrunsfinished-kencama7) | Counter, `{run}` | Run ends by `workflow.name` and `workflow.run.status`, recorded by the observer `Instrumentation.RunFinished()` returns; delivery is at least once, so a redelivered end counts again | [Count run ends](../observability/opentelemetry.md#count-run-ends) |
| `workflow.queue.depth` | [`otel.MetricQueueDepth`](ds:block?id=otel-metricqueuedepth-fgtkqkfz) | Observable gauge, `{run}` | Runs waiting per queue, read at each collection through `Instrumentation.ObserveQueueDepth(fn)` (for example `admin.Admin.QueueDepths`) | [Queue wait and queue depth](../observability/opentelemetry.md#queue-wait-and-queue-depth) |

Spans are named `workflow.step <workflow>/<step>` per step attempt and `workflow.enqueue <workflow>` per enqueue, unless renamed with `WithStepSpanName` and `WithEnqueueSpanName` ([Span names](../observability/opentelemetry.md#span-names)). The step metrics carry `workflow.name`, `workflow.step`, `workflow.queue` and `workflow.outcome`, the enqueue counter `workflow.name` and `workflow.outcome`, plus `workflow.queue` when `Job.Queue` is set; run IDs never become metric attributes.
